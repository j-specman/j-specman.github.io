# j-specman.github.io

Source of the Specman website, published at https://j-specman.github.io/ with GitHub Pages. The site consists of three parts:

* the landing page and a growing amount of additional static content,
* the online manual (HTML and PDF), built from the Specman repository,
* the release history, built from the release notes collected in this repository.

The online manual and the release history come from a tricky but easy-to-use semi-automation, which is explained below. It is related to the release publishing process of Specman, which is described in the https://github.com/j-specman/specman/blob/master/howto/howto-release.adoc[release how-to] of the Specman repository (in German).

## Repository layout

[cols="1,2"]
|===
|Path |Content

|`index.html`, `css/`, `assets/` |Landing page and its styles and images
|`manual-theme/` |Docinfo which gives the manual the header of the site
|`releasenotes/` |Release notes, one Markdown file per release. They are the source of the release history.
|`releasenotes-theme/` |Pandoc template of the release history pages
|`tools/ReleaseHistory.java` |Builds the release history pages. It is started directly from its source with `java`, there is no compile step. The Javadoc explains why.
|`pom.xml` |Maven build of the manual and the release history, see <<Publishing operations>>
|`.github/workflows/deploy-specman-website.yaml` |Build and deployment with GitHub Pages
|===

## Why Maven?
Whenever a new release of Specman is published, some recurring work has to be done in the website repository. To keep this work simple, it is semi-automated, using tools which are available anyway if the maintainer works on the Specman code as well. This is typically the case, so Maven is assumed to be available.

Besides Maven, the build operations need a JDK (21 or higher) and a running Docker, both of which are also required for publishing releases in the Specman repository. The additional tools Asciidoctor and pandoc run in Docker containers and don't have to be installed.

## Publishing operations
Changing static content usually doesn't require running any Maven-based build operation, because all the work is done by GitHub Pages and the GitHub Actions workflow defined in `.github/workflows/deploy-specman-website.yaml`. The workflow is triggered automatically by a push to `main`, so the updated content is visible on the website a few minutes later.

Maven is only required for the following two operations. Both expect a clone of the Specman repository next to this one, in `../specman`. Another location is given with `-Dspecman.clone=<path>`.

### Collect release notes

[source,shell]
----
mvn antrun:run@collect-release-notes
----

This operation collects the release notes of new Specman releases. The notes are written in the Specman repository (`releasenotes/`) when a release is prepared. After the release has been published, the Maven operation above copies them from the Specman clone into `releasenotes/` of this repository. Afterward, the maintainer commits and pushes the new files, which triggers the workflow.

Only files which don't exist in `releasenotes/` yet are copied. The notes in this repository take precedence over the copies in the Specman repository: corrections of published notes are made here, and a re-collected copy never overwrites them. This is helpful for later corrections of the release note content for the history on the website. The release notes in the Specman repository are part of the release branch and should not be changed afterward.

Release note files are supposed to follow a particular format in the first two lines. See chapter <<Release note format>> below.

### Local manual and release history build

[source,shell]
----
mvn package
----

This operation assembles the manual (HTML and PDF) and generates the release history locally, as the `deploy-specman-website.yaml` workflow does it automatically. It is intended for quality checks, e.g. if the manual has changed significantly and the HTML and PDF result should be reviewed before publishing.

The result is written to `_site/manual/` and `_site/releasenotes/`. The workflow copies `index.html`, `css` and `assets` into `_site` as well, so the pages only look like on the real site if these are copied there too.

The manual is built from `doc/specman-manual.adoc` in the Specman clone, so locally it shows whatever is checked out there.

## Release history assembly

The release history pages are generated by `tools/ReleaseHistory.java`. For each file `releasenotes/release-notes-<version>.md`, it creates an HTML page. In addition, it creates an `index.html` listing all releases, newest first, with the release date taken from the `Released:` line (see <<Release note format>>). The Markdown is converted by pandoc in a Docker container, using the page template `releasenotes-theme/template.html`. The program stops with an error message if a file doesn't follow the format or if Docker isn't available. Maven starts it in the `package` phase (execution `release-history` in `pom.xml`), and the pages are written to `_site/releasenotes/`.

### Why Java?
Copying files and calling pandoc could be done with a few lines of shell script, but the maintainers work on Windows, where a shell script can't be assumed to run. Maven alone can't do the job easily either: The index needs the versions sorted numerically, so that `1.10.0` comes after `1.9.0`, and sorting by name gets that wrong. Since a JDK is required for Maven anyway, a small Java program doesn't add any new tool.

The program is not compiled by Maven, and there is no class file or jar. Since Java 11, the `java` launcher can compile and run a single source file in memory. This is how Maven starts the program:

[source,shell]
----
java tools/ReleaseHistory.java releasenotes _site/releasenotes releasenotes-theme/template.html pandoc/core:3.8
----

The arguments are the directory with the release notes, the output directory, the pandoc template and the Docker image providing pandoc. The Javadoc of the class explains them as well.

Be aware that a Java program like this has to reside in a single file (with JDK 21) and must not use any libraries besides the JDK. This is why the program consists of static methods in a single class instead of several small classes.

### Release note format
The release history assembly expects the Markdown release note files to follow a particular format in the first two lines. The release notes are named `releasenotes/release-notes-<version>.md`, for example `release-notes-1.4.0.md`. A file has to start like this:

[source,markdown]
----
## Specman 1.4.0
Released: 2026-11-07
----

The line `Released: <ISO date>` is required, the build fails without it. The index lists the releases by version, newest first, with the date behind the version.

## Pinning the source branch
Any local publishing work refers to a clone of the Specman repository, which is expected to be next to this clone directory in `../specman`. It is up to the maintainer which branch is checked out there. See above for how to change the location.

However, the automatic deployment workflow based on `.github/workflows/deploy-specman-website.yaml` must explicitly be pinned to the branch which is supposed to represent the "latest release" - for example `1.4.x`. The branch to use is defined by the `ref` line in the YAML. It is usually not `master`, because right after publishing a release, the work on `master` goes on and already contains the unreleased development of the next release. Changes of the manual only show up on the website if they are made on the pinned branch.

The https://github.com/j-specman/specman/blob/master/howto/howto-release.adoc[release how-to] of the Specman repository describes the rules when and how to change the pinned branch depending on the type of release publishing.

## Automatic and manual deployment

As already mentioned, a push to `main` automatically triggers the workflow `Deploy Specman Website`, which builds the site and publishes it.

The triggers are defined in the `on:` section at the top of `.github/workflows/deploy-specman-website.yaml`:

[source,yaml]
----
on:
  push:
    branches: [main]
  workflow_dispatch:
----

`push` with `branches: [main]` starts the workflow whenever commits are pushed to `main`, no matter which files have changed. Pushes to other branches don't trigger it. `workflow_dispatch` makes the workflow startable manually: It adds the *Run workflow* button on GitHub, which is used below.

GitHub finds the workflow by convention, it doesn't have to be registered anywhere: Every YAML file in the directory `.github/workflows/` of a repository is a workflow. The file name is free, the name shown on GitHub is the `name:` in the file. On the other hand, there is one setting which is not part of the repository content: In the repository settings under *Pages*, *Build and deployment*, the source has to be *GitHub Actions*. Otherwise GitHub would publish the files of a branch directly, instead of the result of this workflow.

### Manual workflow start
Sometimes nothing is to be committed here, but the website has to be rebuilt anyway, e.g. when only the manual on the pinned release branch has changed. In this case, the workflow can be started manually, assuming write access to the repository:

. Open the repository https://github.com/j-specman/j-specman.github.io in the browser and switch to the tab *Actions*.
. Select the workflow *Deploy Specman Website* in the list on the left.
. Open the *Run workflow* dropdown above the list of runs on the right, select the branch `main` and press the green button *Run workflow*.
. Reload the page after a moment. The new run appears at the top of the list, with a yellow dot while it is running and a green check mark when it is done. This takes a few minutes. After that, the updated content is visible on the website.
. If the run fails (red cross), open it to see in which step it failed.
